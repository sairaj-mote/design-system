THE SYSTEM · FROM PRODUCT TO PROOF

One system. Seventeen product contexts.

Finance, identity, content, social and blockchain tools each ask for different interface decisions. This is how I connect those decisions to a shared, inspectable UI foundation.

The problem

Seventeen products. Each with its own button styles, colour palette, and spacing rules. Every new feature required rediscovering decisions made three products ago — and the inconsistency was visible to users. The design system started as a question: what if we named everything once?

Color

Color starts with two brand ramps — a teal primary and an amber secondary — plus a neutral ramp for surfaces and text. Every color in the product is a token from these ramps, and every token is checked for accessible contrast against its intended background.

Semantic colors

Semantic colors flip between light and dark themes automatically. They always carry meaning — success, warning, danger, info — and are never used for decoration.

Theme tokens

These role tokens are what components actually consume. They map to palette tokens and change value with the theme, so components never have to know whether the app is in light or dark mode.

Typography

Three typefaces, one clear job each: Poppins for display and hierarchy, Roboto for long-form body copy, and Roboto Mono for anything numeric or code-like. We use a modular scale with a fixed set of sizes — no one invents a font size.

Type families

Type scale

Rules of thumb

Line length

Keep body copy at ~65 characters or less for comfortable reading.

Hierarchy

Use the scale's weights and sizes — never fake hierarchy with color alone.

Mono

Use Roboto Mono for numbers, hashes, addresses and code so digits align.

Accessibility

Body text must meet WCAG AA contrast (4.5:1) against its background.

Spacing & layout

Spacing runs on a 4px base grid. Every gap, margin and padding in the system is a step on this scale — that's what makes layouts feel rhythmically consistent even when the content changes.

Breakpoints

The system adapts across three breakpoints. Layouts start mobile-first and scale up.

Layout rules

Grid

Content sits on a fluid grid; columns collapse to one on mobile.

Gutters

Use space-4 (16px) as the default page gutter, space-5 (24px) for larger panels.

Touch targets

Interactive targets aim for a minimum 24px hit area (44px recommended on touch).

Alignment

Prefer multiples of the base grid so elements line up across components.

Radius & elevation

Radius is intentionally small — the system reads as clean and honest, not bubbly. Elevation is expressed through soft shadows that scale with importance, from resting cards up to modal popups.

Motion

Motion is functional, not decorative. It communicates state changes, direction and hierarchy, and it respects prefers-reduced-motion. We keep a deliberately small vocabulary of durations and curves.

Durations

Easing

Motion principles

Fast for feedback, slow for transitions. Hover and micro-interactions use 100ms; page and popup changes use 300ms. If a motion doesn't help the user understand the interface, it doesn't ship.

Iconography

Icons live on a 24×24 grid with consistent stroke weight. They're used as functional aids — reinforcing meaning, never replacing it. Status is always conveyed by color and an icon or label, never color alone.

Usage rules

Grid

All glyphs draw on a 24×24 viewBox; sizes are 16 / 24 / 32px.

Labels

Icon-only buttons must have an accessible label or tooltip.

Meaning

Use the established glyph for an action — don't redraw familiar icons.

Component specs

A spec is the contract between design and engineering. It defines what a component is made of (anatomy), how it can look (variants), how it can behave (states), its public API, and the rules for using it well. These are the specs for our most-used components — everything here is rendered from the real components, so what you see is what ships.

Design practice

A component library is only useful when it improves the experience. My working lens is to understand the job, make each state legible, test the edges, and leave a clear contract for the next person who builds on it.

From problem to product

01

Frame the job

Define who is acting, what they are trying to accomplish, and what uncertainty or friction stands in the way.

02

Map the states

Design the first view, loading, empty, error, disabled, success, focus, and recovery states before polishing the happy path.

03

Compose the system

Choose the smallest existing primitives that make the flow coherent, then document the reason for any new pattern.

04

Prove the edges

Check keyboard flow, content extremes, narrow screens, dark mode, reduced motion, and real feedback from the interface.

Case-study snapshot

Challenge

Make a frameworkless UI library feel dependable enough for repeated product work, not merely attractive in isolation.

Approach

Centralise tokens, expose live Web Components, document behavior as a contract, and verify accessibility and responsive behavior in the browser.

Outcome

A browsable system where visual decisions, implementation details, and experience quality can be inspected in the same place.

Ship criteria

  • The primary task is understandable without a tutorial.
  • Every meaningful state has a designed response.
  • Keyboard and assistive technology paths are usable.
  • Content survives narrow widths and high zoom.
  • Tokens, markup, and documentation agree with the shipped component.
  • There is a clear reason to add or change the pattern.

Accessibility

Accessibility is a first-class requirement of the system, not a compliance checklist. Every component is built and documented against these standards so products built on the system inherit them for free.

Standards we hold

Contrast

Text meets WCAG AA (4.5:1); large text and UI components meet AA large (3:1). All tokens are checked — the badges on the color page show measured ratios.

Keyboard

Everything is reachable and operable by keyboard: Tab to move, Enter/Space to activate, arrow keys in selects, menus and tabs, Esc to dismiss popups.

Focus

A clearly visible :focus-visible indicator ships with every interactive element. Focus is never removed or hidden.

ARIA

Landmarks, labels and live regions are wired into components — notifications announce to screen readers, icons are decorative with text alternatives where needed.

Reduced motion

The system respects prefers-reduced-motion: decorative animation stops, essential transitions remain.

Target size

Interactive targets are at least 24px, with 44px recommended for touch — spacing tokens make this easy to honour.

Why this matters

When accessibility lives in the system instead of the app, every product built on it starts accessible and stays accessible. It's the highest-leverage accessibility work a design system can do.

Getting started

  1. Pick a layout from the Layouts folder — it includes the utilities, components and theme toggle.
  2. Add the components you need from the component library.
  3. Drop tokens/tokens.css into your project and customize the palette in one place.
  4. Follow the dos and don'ts and the accessibility standards.
